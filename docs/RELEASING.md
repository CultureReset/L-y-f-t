# Releasing to Google Play

Both apps ship from the same monorepo and follow the same steps. Everything
below is reproducible from a clean checkout; nothing depends on a machine
someone set up once and forgot.

## What is already done

- **Icons, adaptive icons, splash, and store graphics** are generated from one
  definition by `python3 tools/brand/src/generate.py`. Changing a brand colour
  or the mark means editing `tools/brand/src/generate.py` and re-running it —
  never hand-editing a PNG.
- **`app.json`** carries the package name, `versionCode`, target SDK 35, the
  adaptive icon, and the permission list for each app.
- **`eas.json`** defines three profiles: `development` (dev client, points at
  the emulator's host loopback), `preview` (internal APK against staging), and
  `production` (an app bundle against production).
- **Permissions neither app uses are blocked** in both. A dependency's manifest
  is merged into yours, so a library you use for one small thing can add a
  permission you then have to justify to Play. `blockedPermissions` in
  `app.json` removes them:
  - `AD_ID` — neither app collects an advertising ID, and declaring it would
    force a "yes" on the Data safety advertising question.
  - `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` — added by
    `expo-file-system`, which neither app uses outside its own sandbox. Broad
    storage access needs a declaration neither app could honestly make.

  Two permissions do survive and are correct: `RECEIVE_BOOT_COMPLETED`, which
  `expo-notifications` needs to restore scheduled notifications after a
  restart, and the launcher badge permissions, which are how a badge count
  reaches the home screen on Samsung, Huawei, and Oppo devices.

  Verify what actually shipped, rather than what you declared:

  ```bash
  $ANDROID_HOME/build-tools/35.0.0/aapt2 dump permissions \
    apps/rider/android/app/build/outputs/apk/debug/app-debug.apk
  ```

  A debug build additionally carries `SYSTEM_ALERT_WINDOW`, which React
  Native's dev menu needs; it is absent from a release build. Check a release
  build before submitting.

## Building

```bash
# A local debug APK, no account needed. Requires ANDROID_HOME.
cd apps/rider && npx expo prebuild --platform android && \
  cd android && ./gradlew assembleDebug

# A release bundle through EAS.
cd apps/rider && npx eas build --platform android --profile production
```

The generated `android/` directory is not tracked: it is derived from
`app.json` and regenerated by `expo prebuild`. Never edit it by hand — the next
prebuild discards the change.

## Signing

Play App Signing holds the release key. EAS generates and stores the upload
key on the first production build; `npx eas credentials` shows or rotates it.

Building release APKs locally instead requires a keystore that is **never**
committed:

```bash
keytool -genkeypair -v -keystore upload.jks -alias upload \
  -keyalg RSA -keysize 2048 -validity 10000
```

Put its path and passwords in `~/.gradle/gradle.properties`, not in the repo.

## Before every submission

1. Bump `expo.android.versionCode` in `app.json`. Play rejects an upload whose
   `versionCode` has not increased, and this is the step that gets forgotten.
2. Bump `expo.version` when the change is user-visible.
3. `npm test` and `npm run typecheck` from the repo root.
4. Point the build at the right API: `EXPO_PUBLIC_API_URL` in the chosen
   `eas.json` profile. A production build against a staging API is the most
   expensive mistake available here.
5. Check `docs/store/<app>/listing.md` still describes what the app does.

## Permissions, and how to justify them

Play asks about every sensitive permission. These are the answers, and each is
tied to a specific screen rather than a general claim.

### Rider app

| Permission | Why |
| --- | --- |
| `ACCESS_FINE_LOCATION` | Sets the pickup point on the confirm screen and shows the driver approaching on the live ride screen. |
| `ACCESS_COARSE_LOCATION` | Fallback when the rider denies precise location; the pickup can still be set approximately and corrected by hand. |
| `FOREGROUND_SERVICE` | Keeps the ride's realtime connection alive while the trip is in progress and the app is backgrounded. |
| `POST_NOTIFICATIONS` | "Your driver is arriving", trip updates, and receipts. Asked for after sign-in, not on first launch. |
| `VIBRATE` | The alert pattern for an arriving driver. |

The rider app requests **no background location**. A rider's location matters
only while the app is open.

### Driver app

| Permission | Why |
| --- | --- |
| `ACCESS_FINE_LOCATION` | Position is the input to dispatch: it decides which offers a driver receives and is shown to the rider as the car approaching. |
| `ACCESS_BACKGROUND_LOCATION` | A driver's phone is mounted and the screen sleeps. Without it, a trip in progress stops updating the rider entirely. **Play requires a video demonstrating this**; record the drive screen going to background mid-trip while the rider app keeps tracking. |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION` | The persistent notification that makes background location lawful and visible. |
| `WAKE_LOCK` | Keeps the offer countdown running when an offer arrives on a sleeping device. |
| `POST_NOTIFICATIONS` | Ride offers, which are the product. Asked for after sign-in. |
| `VIBRATE` | The alert pattern for an incoming offer. |

## Data safety declarations

Answer the form from this table. It reflects what the code actually does; if a
row stops being true, the code changed and the form needs revisiting.

| Data type | Collected | Shared | Purpose | Optional |
| --- | --- | --- | --- | --- |
| Approximate location | Yes | Yes — with the matched driver or rider | App functionality | No |
| Precise location | Yes | Yes — with the matched driver or rider | App functionality | No |
| Name | Yes | Yes — first name and last initial only | App functionality | No |
| Phone number | Yes | No | Account management | No |
| Email address | Yes | No | Receipts | Yes |
| Payment info | Yes | Yes — with the payment processor | App functionality | No |
| Messages | Yes | Yes — with the other party on the trip | App functionality | Yes |
| Photos | Yes (driver documents) | No | Account management, safety | No |
| Crash logs | No | No | — | — |
| Advertising ID | No | No | — | — |

Push tokens are device identifiers, not personal data, and are declared under
**Device or other IDs → collected, not shared**. They are pruned the moment
Expo reports a device as unregistered.

Both apps encrypt data in transit and offer account deletion in-app
(rider: Help → Account → Deleting your account).

## Store listing

`docs/store/<app>/listing.md` holds the title, short description, full
description, and the screenshot inventory. Graphics are in the same folder:

- `play-icon-512.png` — 512×512, the listing icon.
- `play-feature-graphic.png` — 1024×500, no transparency.
- Screenshots: at least two per form factor, 16:9 or 9:16, 320–3840px per side.
  Capture them from a running build rather than mocking them up.

## Content rating and policy

- Both apps are **Everyone**; there is no user-generated public content.
- The driver app collects identity documents, so the listing must link a
  privacy policy that covers them — see `docs/PRIVACY.md`.
- A ridehail app in most markets also needs the operator's licence details in
  the listing. That is a business fact, not a code one; fill it in per market.
